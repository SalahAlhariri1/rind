# Rind on Zetaris: the Unified Semantic Layer

This document follows the Zetaris evaluation criteria. Part 1 is the build; part 2 is the reflection.
The evidence for part 1 is produced by running `python scripts/zetaris_usl_report.py`, which writes
`evidence/zetaris_usl_report.md`.

All data is **synthetic** (generated by `scripts/generate_data.py`, seed 42) and contains no real people or companies.

---

## 1. Build a Unified Semantic Layer

### 1a. Use case and data sources

**User:** a customer success manager (CSM) at a B2B software company with a book of about 60 accounts.
**Problem:** the CRM health score says an account is fine while the real warning signs sit in other systems.
CS teams call these *watermelon accounts*: green outside, red inside.
**Agent:** Rind checks every account across five systems each week, argues itself out of false alarms,
and gives the CSM a short list with reasons and sources.

| # | System (Lightning database) | What it holds | Customer key in that system |
|---|---|---|---|
| 1 | `RIND_CRM` → `rind.crm_accounts` | Accounts, ARR, renewal date, health score and colour | `account_id` (ACC-1047) |
| 2 | `RIND_USAGE` → `rind.product_usage` | Weekly active users, seats, sessions (32 weeks: the last 16 and the same 16 a year earlier) | `account_ref` (acc1047) |
| 3 | `RIND_SUPPORT` → `rind.support_tickets` | Tickets, priority, status, sentiment | `org_domain` (maplecrestlogistics.example) |
| 4 | `RIND_BILLING` → `rind.billing_invoices` | Invoices, due and paid dates | `customer_no` (C-12345) |
| 5 | `RIND_CONTACTS` → `rind.contacts` | Champions, sponsors, admins, job changes | `company_domain` |

Five sources (minimum is three), deliberately with **four different customer keys**, because that is what
real CS data looks like.

### 1b. Onboarding, verification and exploratory queries

- `scripts/register_zetaris_sources.sql` creates the five Lightning databases, one Lightning REST table per
  system (each reads a JSON export over HTTPS), and one SchemaStore view per system in container `rind`
  (`LATERAL VIEW explode(data)` flattens the export and casts types).
- `scripts/setup_zetaris.py` runs it one statement at a time and verifies row counts per view.
- `scripts/zetaris_usl_report.py` asks **three questions of each source (15 total)**, e.g. *Which green accounts
  renew in the next 90 days?*, *Which customers habitually pay after the due date?*, *Which champions left,
  and where did they go?* The SQL and the answers are in the report.

### 1c. The USL, its DDL, proof it is active, and a data quality rule

- **USL:** the five `rind.*` views plus the federated view **`rind.account_360`**, which joins CRM, billing and
  support on three different keys. **DDL:** `scripts/register_zetaris_sources.sql`.
- **Active:** the agent itself runs on the USL. Every weekly run sends 7 queries to Zetaris
  (roster, usage, last year's usage, tickets, invoices, contacts, `account_360`); every query, its row count and
  latency are in the run trace (`logs/run_<id>.jsonl`, event `sql`). The report adds three questions only the
  unified layer can answer in one query, such as *green in the CRM but red in billing or support*.
- **Data quality:** `scripts/zetaris_quality_rules.sql` defines **8 rules, one SchemaStore view each** (`rind.dq_*`), for example
  *every invoice, ticket, usage row and contact maps to a CRM account* (catches a broken customer key, which
  would make an account silently look healthy), *health score between 0 and 100*, and
  *no invoice due before it was issued*. The report creates the views and executes each one; every rule shows
  rows checked, violations and PASS/FAIL.

## 2. Reflect on the USL

### 2a. How the USL saved time compared with a hand-coded approach

**What the hand-coded version would need.** Without the USL, Rind would need its own client for each of the
five exports, code to flatten and type each one, a mapping table for four customer keys, join and aggregation
code, a cache, and a different code path for every new question the agent asks. Every one of those becomes
something the agent's code depends on.

**What the USL gave us instead.**
- One access point and one language. The agent asks every question as SQL through one REST endpoint,
  so adding a check is adding a query, not a new integration.
- The joins live in one place. `rind.account_360` was written once; the agent, the report, the data quality
  rules and any SQL client reuse it.
- Swapping a source is a DDL change. Replacing a JSON export with a real CRM connection changes the
  REST table, not the agent.

**Bonus: a hand-coded part, compared.** `handcoded_account_360()` in `scripts/zetaris_usl_report.py` rebuilds
`rind.account_360` in plain Python from the same exports. The report runs both and compares every account
(the sample-mode run matched **60 of 60**). The interesting difference is not line count (the Python is about
2x the SQL); it is that the Python version is usable only by that one script, has to be re-run to see new data,
and would have to be rewritten for each new question, while the view is shared by everything that speaks SQL.

**Where the USL did not save time (honest notes).**
- Per-account derived facts (usage trend vs. the prior 8 weeks, the same weeks last year, "always pays late")
  are still computed in Python (`agent/data.py`) on rows pulled from the views. They would be better as views.
- REST tables re-fetch the source on every query, so we added `CACHE TABLE` for the largest view and cut
  each run to 7 bulk queries instead of one per account.
- Statements must be sent one at a time, so setup needs a small runner script.
- A REST-backed view flattened with `LATERAL VIEW explode` cannot appear twice in one query (Spark reports
  `MISSING_ATTRIBUTES.RESOLVED_ATTRIBUTE_APPEAR_IN_OPERATION`). Our first data quality view combined all rules with
  `UNION ALL` and failed on live Zetaris, so each rule became its own view, and a "latest week" question uses a window
  function instead of a self-referencing subquery.

Our rough estimate, not a measurement: the USL saved about a day of a six-day build, mostly in not
writing and debugging per-source loaders and key mapping.

### 2b. How the USL would help, or not, in real work

**Where it helps: a customer success team.** The data a CSM needs is spread across the CRM (e.g. Salesforce),
product analytics, the help desk, billing and a people directory. Today a thorough weekly check means opening
five tools per account, which is why nobody does it and watermelon accounts surprise teams at renewal.
A USL turns "is this account really healthy?" into one query that an agent like Rind, a dashboard or an analyst
can all reuse, without copying the data into yet another warehouse.

**Bonus: a project that would benefit, with a forecast.** *Renewal risk review for a CS org of 10 CSMs × 60 accounts.*
Assumptions (estimates, not measured): a manual cross-system check takes about 2 minutes per system per account;
teams realistically check only accounts renewing within 90 days (about a quarter of the book).
- Manual: 15 accounts × 5 systems × 2 min ≈ **2.5 hours per CSM per week**, about 25 hours across the team,
  and the other 45 accounts per CSM go unchecked.
- With the USL + Rind: the whole book is checked every week; the CSM reviews only the flagged accounts with
  their reasons, about 30 minutes. Forecast saving: roughly **20 hours per week for the team**, plus coverage of
  accounts that are never checked today.

**Where it would not help much.** A team whose data already lives in one system; sub-second real-time scoring
(REST-backed tables re-fetch the source); and sources whose records share no key at all, where entity
resolution has to happen first (see 2c).

### 2c. How to make the USL stronger: a killer requirement

**Requirement (written as a PM): "Customer entities with key mappings in the USL."**

> *As a data engineer building an agent across business systems, I want to declare once that
> CRM `account_id`, usage `account_ref`, billing `customer_no` and help-desk `org_domain` are the same customer,
> so that every view, agent and rule can join on "customer" without re-implementing key mapping,
> and so that Zetaris tells me automatically when a record no longer maps to any customer.*

**Why it is the killer feature.** Every multi-system agent hits this on day one. In Rind, four of the eight data
quality rules exist only to catch broken key mappings, and every cross-system query repeats the mapping logic
(`CONCAT('acc', SUBSTRING(account_id, 5))`, domain matching, customer numbers).

**Acceptance criteria.**
1. Declare an entity with one key column per source, including simple transforms.
2. Query by entity: `JOIN ... USING ENTITY customer`, or a generated `customer_360` view.
3. Built-in coverage check: rows per source that map to no entity, exposed as a system view.
4. The mapping is versioned with the USL, so agents and rules always use the same definition.

**Bonus: a mock of the feature** (*illustrative syntax, not real Zetaris SQL*):

```sql
-- MOCK: proposed syntax
CREATE SCHEMASTORE ENTITY customer WITH CONTAINER rind
  KEY rind.crm_accounts.account_id                          AS primary
  KEY rind.product_usage.account_ref  MAPS crm_accounts.account_id VIA CONCAT('acc', SUBSTRING(account_id, 5))
  KEY rind.billing_invoices.customer_no MAPS crm_accounts.billing_customer_no
  KEY rind.support_tickets.org_domain   MAPS crm_accounts.domain
  KEY rind.contacts.company_domain      MAPS crm_accounts.domain;

-- account_360 then needs no hand-written join keys:
CREATE SCHEMASTORE VIEW account_360 WITH CONTAINER rind AS
SELECT customer.account_id, customer.account_name, customer.health_color,
       SUM(billing_invoices.status = 'overdue')                         AS overdue_invoices,
       SUM(support_tickets.status <> 'solved'
           AND support_tickets.priority IN ('high', 'urgent'))         AS open_high_tickets
FROM ENTITY rind.customer
GROUP BY customer;

-- and the four key-mapping quality rules become one system view:
SELECT source, unmapped_rows FROM rind.customer$coverage;
```

**Two smaller requests from building Rind.**
- *Metric definitions with time windows*, e.g. "weekly active users, last 4 weeks vs. the 8 before, and the same
  weeks last year", declared once in the USL instead of computed in each app.
- *A cache policy per REST table* (e.g. refresh hourly), so agents don't re-fetch a source on every query.
- *Allow a REST-backed view to be used twice in one query* (self-joins, `UNION ALL` of checks, "latest week"
  subqueries), which fails today with `MISSING_ATTRIBUTES.RESOLVED_ATTRIBUTE_APPEAR_IN_OPERATION`.

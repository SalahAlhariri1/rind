# Rind data

All data is **synthetic** (fictional companies, people and numbers), generated by
`scripts/generate_data.py` (seed 42). No real personal or customer data is used.

| File | System it imitates | Customer key | Rows |
|---|---|---|---|
| `sources/crm_accounts.json` | CRM (account, stale health score, renewal, notes) | `account_id` (hub: also holds `domain`, `billing_customer_no`) | 60 |
| `sources/product_usage.json` | Product analytics (weekly active users, this year + same weeks last year) | `account_ref` (`acc1001`) | 1,920 |
| `sources/support_tickets.json` | Help desk | `org_domain` | ~200 |
| `sources/billing_invoices.json` | Billing (quarterly invoices, payment dates) | `customer_no` + `legal_name` | 240 |
| `sources/contacts.json` | People directory with job-change signals | `company_domain` | ~180 |

Each file is `{"system": ..., "exported_at": ..., "record_count": n, "data": [ ... ]}`.

**How it gets into Zetaris:** the files are served over HTTPS from this public repo and
registered as Lightning REST tables, one Lightning database per system, then flattened
into SchemaStore views in the `rind` container (`scripts/register_zetaris_sources.sql`,
run by `scripts/setup_zetaris.py`). Zetaris cannot read files on a laptop, which is why
they are served from the repo.

**Ground truth** (`eval/ground_truth.json`) labels each account: 8 watermelons (green CRM
score, 2-3 real churn signals), 5 already-red accounts, 12 decoys (4 seasonal dips,
3 habitual late payers, 3 solved urgent tickets, 2 replaced champions) and 35 healthy.
It is used only by `eval/run_eval.py`; agents never see it.

**Regenerate:** `python scripts/generate_data.py`

**Licence:** generated for this project, MIT like the code. **Limitations:** synthetic
patterns are cleaner than real CRM data; weekly granularity; one CSM's book of 60 accounts.
